# Методология расчёта Finplex

Подробности для технической проверки. Пользовательский сценарий и запуск описаны в [README](../README.md). Отдельные складские данные — в [контракте импорта](WAREHOUSE_IMPORT.md), утверждённые заказы — в [контрактах CSV/JSON](1C_EXPORT.md).

## Источники и правила импорта

У каждого поставщика используются все шесть приложенных Excel: динамика, месячные продажи, месячные остатки, товар в пути, MOQ и сезонность. Заголовки ищутся по названиям обязательных полей. Неверные числа, противоречивые дубли и отсутствующие заголовки дают ошибку, а не пустой справочник.

- Положительная расходная накладная — продажа. Отрицательная строка сохраняется как коррекция, возврат нормализуется в отрицательное количество. Неизвестные типы документов/невалидные даты исключаются с числом отклонённых строк в `history_quality`. Эта интерпретация видима и должна быть подтверждена владельцем выгрузки; суммы сверяются со сводными продажами.
- Основной ряд — месячная сводка. Она не складывается с историей накладных. Список SKU включает товары только из истории; пропущенные и более новые месяцы восстанавливаются из накладных. Начало окна задаётся сводкой: отдельные более старые накладные не добавляют годы с фиктивными нулями. Для SKU вне сводки используется доступная история накладных внутри окна; это отмечено отдельно. Будущие накладные после даты расчёта исключаются. Отсутствие продажи внутри доступного окна — ноль, отсутствие остатка — неизвестное значение.
- Код 1С и артикул поставщика сохраняются раздельно. Недостающие реквизиты сопоставляются по точному коду из сводки, остатков, пути и истории: автоматическая подстановка допустима только при одном уникальном значении. Противоречия дают предупреждение. Если артикул или единица отсутствуют, менеджер заполняет их в рекомендации по проверенному справочнику. Без них создание заказа недоступно. В заказе сохраняются исходные и уточнённые значения (`manual_requisites`); исходный план не изменяется.
- Кратность Systeme и минимальная отгрузка ИЭК — разные правила: `pack_size` и `min_qty`. Совпадающие правила дублированного кода объединяются; конфликты отклоняются. Повторы строк пути не суммируются повторно в рамках одной колонки поставки.
- У Systeme текущий свободный остаток берётся из витрины. Если витрины для SKU нет, и у ИЭК, используется последний доступный начальный месячный остаток с исходной датой и предупреждением. Он не объявляется текущим остатком.
- ETA ИЭК извлекается из колонок поставок. У Systeme точной ETA нет: такой путь уменьшает общий объём закупки, но не скрывает риск дефицита до поступления; менеджер должен проверить дату. Просроченные неподтверждённые и слишком поздние партии не вычитаются из потребности на срок поставки.
- Версия набора зависит от путей, времени изменения и размеров всех файлов, включая `planning.json` и `warehouses.json`. При обновлении файлов кеш перечитывается. Сохранённые планы содержат дату и версию источников; создание/утверждение черновика по старой версии блокируется.
- `metadata.reconciliation` показывает расхождения SKU-месяцев истории и сводки. Исходные выгрузки действительно расходятся; сервис не скрывает и не «исправляет» это выдуманными продажами.

## Методология

### Выбросы

Сначала продажи группируются по SKU, дню и обезличенному клиенту, если доступен контрактный `customer_id`; иначе — по документу. Отрицательные коррекции не считаются крупными продажами. Порог: `max(median + 3*IQR, 5*median, median + 10)` при не менее четырёх положительных наблюдениях. Нижние пределы защищают случай IQR=0 и небольшие колебания. Повторяющиеся крупные покупки одного клиента в трёх и более месяцах не считаются разовыми.

Обнаруженные объёмы действительно вычитаются из соответствующего месяца. Если итог накладных не совпадает со сводкой более чем на 5% (минимум 1 единица), переносится доля аномальных продаж, а не несопоставимый абсолютный объём; строка получает предупреждение. Это допущение требует проверки при значимых расхождениях.

Повторяющийся оптовый сегмент обрабатывается отдельно: если крупные накладные встречаются минимум в трёх месяцах, порог повторно оценивается внутри этого сегмента. Это предотвращает удаление обычных оптовых продаж только из-за большого числа мелких розничных чеков. Повторяемые календарные пики сделок также защищены.

Дополнительная консервативная очистка месячного ряда заменяет медианой только одиночные пики, превышающие тот же порог. Повторяющийся пик того же календарного месяца и несколько соседних высоких месяцев защищены. Хранятся факт, очищенный ряд и фактически удалённый объём.

### Сезонность и рост

Описание смешанного профиля ниже относится к сводному набору. Для отдельных складов используется собственная история и профиль категории выбранного склада; внешний профиль поставщика заменён нейтральным, чтобы не переносить сводную сезонность без подтверждения.

Используются только полные месяцы на дату расчёта; неполный сентябрь виден на графике, но не обучает прогноз. Сезонный профиль календарных месяцев объединяет собственный профиль SKU, профиль категории и профиль поставщика из отдельного сезонного файла. При истории от 24 месяцев вес SKU 60%, категории и поставщика — по 20%; на короткой истории — 20%/40%/40%. Профили нормируются.

База — средний десезонализированный спрос последних 12 полных месяцев, включая нулевые продажи. Если передан прогноз прироста, используется он. Иначе рост оценивается медианой последних шести сопоставимых год-к-году отношений при минимум четырёх наблюдениях и согласованном знаке не менее 75%. Изменение ограничено ±40%. Прирост не применяется дважды.

Снимковый «Кэф. Сез-ти» витрины не переносится на все будущие месяцы: вместо него используется календарный профиль из полной истории/сезонного файла. Прогноз разных месяцев может отличаться. Сценарий «спрос +20%» умножает спрос, не срок поставки.

### Stockout

Нулевые продажи или нулевой начальный месячный остаток не доказывают длительность отсутствия. По таким данным показывается сигнал проверки, без фиктивной компенсации.

Для подтверждённых `stockout_days` по SKU/месяцу упущенный спрос рассчитывается по скорости продаж в дни наличия, если осталось минимум семь таких дней. Для полного/почти полного отсутствия используется средний спрос того же календарного месяца из доступных полных месяцев; при отсутствии аналогов — среднее остальных месяцев. Эта оценка добавляется к очищенному ряду до прогноза и показывается отдельно. Дни вне истории или сверх длины месяца отклоняются.

### Заказ

`цель = календарный спрос от следующего дня после снимка до конца срока поставки + страховой запас`.

Страховой запас — максимум из `спрос_в_месяц × safety` и `1,65 × σ десезонализированного спроса × sqrt(lead_time)`, с учётом роста/сценария и настроенного множителя категории. Значение `safety=0` не отключает статистическую часть.

`потребность = max(0, цель − свободный остаток − зачтённые поступления)`; затем минимум партии и округление вверх до кратности. Риск дефицита проверяется по дневному балансу наличия и известным ETA. `coverage_months` отражает наличный остаток, не виртуальную сумму с ещё не прибывшим товаром.

Бюджет распределяется по срочности и покрытию; неизвестная стоимость не проходит ограниченный бюджет. Финальная выбранная сумма пересчитывается сервером после правок. Нулевая сумма в KPI при неизвестных ценах означает только известную часть стоимости и сопровождается числом неоценённых позиций.

## Дополнительные проверенные данные

Опциональный `data/<supplier>/planning.json` дополняет исходные файлы. Пример структуры (замените код реальным; не копируйте пример как фактические данные):

```json
{
  "as_of": "2026-09-22",
  "lead_time_months": 1.5,
  "category_policies": {"1": {"safety_multiplier": 1.2}},
  "items": {
    "YOUR_1C_CODE": {
      "article": "SUPPLIER_ARTICLE",
      "unit": "шт",
      "category": "1",
      "cost": 100,
      "free_stock": 20,
      "stock_as_of": "2026-09-22",
      "stock_estimated": false,
      "growth_coef": 0.1,
      "lead_time": 1,
      "stockout_days": {"2026-08": 10},
      "transit_lots": [{"qty": 30, "eta": "2026-10-01"}]
    }
  }
}
```

Глобальный явно введённый срок переопределяет сроки SKU для сценария. По умолчанию интерфейс отправляет `lead_time: null`: используется срок SKU, затем поставщика. Сценарий задержки прибавляет 0,5 месяца к каждому выбранному таким образом сроку, не изменяя исходные данные. Поле `customer_id` в истории допускается только для уже обезличенных идентификаторов. Имена/контакты клиента не загружаются и не пересылаются.
