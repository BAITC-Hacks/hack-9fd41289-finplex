# Finplex — планирование закупок для «Электрокомплект»

Детерминированный расчёт по выгрузкам Systeme Electric и ИЭК. Менеджер получает объяснимые рекомендации, меняет количество/цену, сохраняет черновик, отдельно утверждает его и выгружает CSV. Отправки заказа поставщику нет.

## Запуск

Из корня репозитория:

```sh
docker compose up --build
```

Интерфейс: http://localhost:3100; API: http://localhost:8020. Порты по умолчанию доступны только на локальном компьютере. Данные читаются из `data/`, SQLite с планами и заказами сохраняется в Docker volume `planner-state`.

Без Docker, Python 3.11–3.12, два терминала:

```sh
cd backend
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8020
```

```sh
cd frontend
python -m http.server 3100 --bind 127.0.0.1
```

Локальная БД: `backend/runtime/planner.sqlite3`; путь меняется через `DATABASE_PATH`. Не удаляйте volume/БД, если нужны сохранённые заказы. Для тестов используется отдельная временная БД.

## Сценарий работы

1. Выбрать поставщика, категорию и доступную область склада; проверить дату и предупреждения входных данных.
2. Указать срок поставки, страховой запас и бюджет. Срок 1,5 месяца — явное допущение, а не полученное условие поставщика.
3. Рассчитать. Все рекомендации возвращаются целиком; интерфейс показывает по 100 строк. Выбор и правки сохраняются при поиске и смене страницы.
4. Выбрать позиции, изменить количество и при необходимости цену. Партия и бюджет проверяются также сервером. Неизвестная цена не равна нулевой стоимости.
5. Сохранить черновик. Проверить его отдельную таблицу, указать ответственного и подтвердить проверку данных, затем нажать «Утвердить».
6. Скачать CSV именно этого утверждённого заказа. Повторное открытие доступно в списке сохранённых заказов после перезагрузки страницы/сервера. Чтобы исправить выбор до утверждения, измените рекомендации и сохраните новый черновик; утверждённый снимок неизменяем.

## Источники и правила импорта

У каждого поставщика используются все шесть приложенных Excel: динамика, месячные продажи, месячные остатки, товар в пути, MOQ и сезонность. Заголовки ищутся по названиям обязательных полей. Неверные числа, противоречивые дубли и отсутствующие заголовки дают ошибку, а не пустой справочник.

- Положительная расходная накладная — продажа. Отрицательная строка сохраняется как коррекция, возврат нормализуется в отрицательное количество. Неизвестные типы документов/невалидные даты исключаются с числом отклонённых строк в `history_quality`. Эта интерпретация видима и должна быть подтверждена владельцем выгрузки; суммы сверяются со сводными продажами.
- Основной ряд — месячная сводка. Она не складывается с историей накладных. Для SKU вне сводки используется доступная история накладных; это отмечено отдельно. Отсутствие продажи — ноль, отсутствие остатка — неизвестное значение.
- Товары объединяются по коду 1С без потери позиций, существующих только в одном источнике. Код 1С и артикул поставщика сохраняются раздельно. Единицы берутся из остатков/истории. Отсутствующие артикул и единица блокируют создание заказа до уточнения.
- Кратность Systeme и минимальная отгрузка ИЭК — разные правила: `pack_size` и `min_qty`. Совпадающие правила дублированного кода объединяются; конфликты отклоняются. Повторы строк пути не суммируются повторно в рамках одной колонки поставки.
- У Systeme текущий свободный остаток берётся из витрины. Если витрины для SKU нет, и у ИЭК, используется последний доступный начальный месячный остаток с исходной датой и предупреждением. Он не объявляется текущим остатком.
- ETA ИЭК извлекается из колонок поставок. У Systeme точной ETA нет: такой путь уменьшает общий объём закупки, но не скрывает риск дефицита до поступления; менеджер должен проверить дату. Просроченные неподтверждённые и слишком поздние партии не вычитаются из потребности на срок поставки.
- Версия набора зависит от путей, времени изменения и размеров всех файлов, включая `planning.json`. При обновлении файлов кеш перечитывается. Сохранённые планы содержат дату и версию источников; создание/утверждение черновика по старой версии блокируется.
- `metadata.reconciliation` показывает расхождения SKU-месяцев истории и сводки. Исходные выгрузки действительно расходятся; сервис не скрывает и не «исправляет» это выдуманными продажами.

## Методология

### Выбросы

Сначала продажи группируются по SKU, дню и обезличенному клиенту, если доступен контрактный `customer_id`; иначе — по документу. Отрицательные коррекции не считаются крупными продажами. Порог: `max(median + 3*IQR, 5*median, median + 10)` при не менее четырёх положительных наблюдениях. Нижние пределы защищают случай IQR=0 и небольшие колебания. Повторяющиеся крупные покупки одного клиента в трёх и более месяцах не считаются разовыми.

Обнаруженные объёмы действительно вычитаются из соответствующего месяца. Если итог накладных не совпадает со сводкой более чем на 5% (минимум 1 единица), переносится доля аномальных продаж, а не несопоставимый абсолютный объём; строка получает предупреждение. Это допущение требует проверки при значимых расхождениях.

Повторяющийся оптовый сегмент обрабатывается отдельно: если крупные накладные встречаются минимум в трёх месяцах, порог повторно оценивается внутри этого сегмента. Это предотвращает удаление обычных оптовых продаж только из-за большого числа мелких розничных чеков. Повторяемые календарные пики сделок также защищены.

Дополнительная консервативная очистка месячного ряда заменяет медианой только одиночные пики, превышающие тот же порог. Повторяющийся пик того же календарного месяца и несколько соседних высоких месяцев защищены. Хранятся факт, очищенный ряд и фактически удалённый объём.

### Сезонность и рост

Используются только полные месяцы на дату расчёта; неполный сентябрь виден на графике, но не обучает прогноз. Сезонный профиль календарных месяцев объединяет собственный профиль SKU, профиль категории и профиль поставщика из отдельного сезонного файла. При истории от 24 месяцев вес SKU 60%, категории и поставщика — по 20%; на короткой истории — 20%/40%/40%. Профили нормируются.

База — средний десезонализированный спрос последних 12 полных месяцев, включая нулевые продажи. Если передан прогноз прироста, используется он. Иначе рост оценивается медианой последних шести сопоставимых год-к-году отношений при минимум четырёх наблюдениях и согласованном знаке не менее 75%. Изменение ограничено ±40%. Прирост не применяется дважды.

Снимковый «Кэф. Сез-ти» витрины не переносится на все будущие месяцы: вместо него используется календарный профиль из полной истории/сезонного файла. Прогноз разных месяцев может отличаться. Сценарий «спрос +20%» умножает спрос, не срок поставки.

### Stockout

Нулевые продажи или нулевой начальный месячный остаток не доказывают длительность отсутствия. По таким данным показывается сигнал проверки, без фиктивной компенсации.

Для подтверждённых `stockout_days` по SKU/месяцу упущенный спрос рассчитывается по скорости продаж в дни наличия, если осталось минимум семь таких дней. Для полного/почти полного отсутствия используется средний спрос того же календарного месяца из доступных полных месяцев; при отсутствии аналогов — среднее остальных месяцев. Эта оценка добавляется к очищенному ряду до прогноза и показывается отдельно. Дни вне истории или сверх длины месяца отклоняются.

### Заказ

`цель = календарный спрос от следующего дня после снимка до конца срока поставки + страховой запас`.

Страховой запас — максимум из `спрос_в_месяц × safety` и `1,65 × σ десезонализированного спроса × sqrt(lead_time)`, с учётом роста/сценария и настроенного множителя категории. Значение `safety=0` не отключает статистическую часть.

`потребность = max(0, цель − свободный остаток − зачтённые поступления)`; затем минимум партии и округление вверх до кратности. Риск дефицита проверяется по дневному балансу наличия и известным ETA. `coverage_months` отражает наличный остаток, не виртуальную сумму с ещё не прибывшим товаром.

Бюджет распределяется по срочности и покрытию; неизвестная стоимость не проходит ограниченный бюджет. Финальная выбранная сумма пересчитывается сервером после правок. Нулевая сумма в KPI при неизвестных ценах означает только известную часть стоимости и сопровождается числом неоценённых позиций.

## Дополнительные проверенные данные

Опциональный `data/<supplier>/planning.json` дополняет исходные файлы. Пример структуры (замените код реальным; не копируйте пример как фактические данные):

```json
{
  "as_of": "2026-09-22",
  "lead_time_months": 1.5,
  "category_policies": {"1": {"safety_multiplier": 1.2}},
  "items": {
    "YOUR_1C_CODE": {
      "article": "SUPPLIER_ARTICLE",
      "unit": "шт",
      "category": "1",
      "cost": 100,
      "free_stock": 20,
      "stock_as_of": "2026-09-22",
      "stock_estimated": false,
      "growth_coef": 0.1,
      "lead_time": 1,
      "stockout_days": {"2026-08": 10},
      "transit_lots": [{"qty": 30, "eta": "2026-10-01"}]
    }
  }
}
```

Глобальный выбранный в интерфейсе срок поставки переопределяет сроки SKU для сценария. При отсутствии переопределения API использует срок SKU, затем поставщика. Поле `customer_id` в истории допускается только для уже обезличенных идентификаторов. Имена/контакты клиента не загружаются и не пересылаются.

## Ограничения исходных данных

- Нет обезличенных клиентов и точных дневных stockout: соответствующая логика проверена синтетическими регрессионными тестами, но не подтверждена отсутствующими реальными данными.
- У ИЭК нет цен и актуального снимка свободного остатка на 22 сентября. До утверждения менеджер должен обновить/проверить остаток и заполнить цены. Цены можно вводить в черновике; остальные уточнения — через `planning.json` и пересчёт.
- Нет согласованной модели спроса/резервов каждого склада. Доступна только честно обозначенная сводная область, а неподтверждённые автоматические перемещения отключены. Делить агрегированный спрос произвольно между складами нельзя.
- CSV UTF-8 BOM с разделителем `;` содержит код 1С, артикул, поставщика, название, единицу, количество, цену, сумму, объяснение и срочность. Это обменный формат; специфичный обработчик импорта вашей конфигурации 1С нужно согласовать отдельно. CSV экранирует кавычки и опасные формульные префиксы.
- Алерты получают полный снимок SKU, включая восстановленные остатки. Отключение категории/склада действует; повторный дефицит после восстановления снова уведомляет. Лента доступна через API, хранится в памяти и сбрасывается при перезапуске; email — только лог, не реальная рассылка.
- Эвристика аномалий и прогноз требуют калибровки на согласованных данных. Сервис не обещает доказанное снижение дефицита без проверки на истории.

## Проверки

Из `backend` после установки `requirements-dev.txt`:

```sh
python -m pytest
ruff check app tests
python -m app.backtest --supplier systeme --products 30 --months 3
python -m app.backtest --supplier iek --products 30 --months 3
```

Тесты включают реальные файлы обоих поставщиков, IQR=0, сезонные пики, транзакционные/клиентские выбросы, подтверждённый и неподтверждённый stockout, MOQ, ETA, отсутствие цены, бюджет, сохранение и утверждение заказа, CSV, неверные параметры, API-ключ и смену версии входов. Реальные файловые тесты пропускаются, если партнёрские файлы отсутствуют.

Backtest использует последовательные месячные отрезки; набор товаров выбирается по обучающей истории, текущие цены/остатки/коэффициенты роста не используются для прогноза прошлых периодов. Показывает WAPE и недо-/перепрогноз относительно наблюдавшихся продаж против seasonal-naive (тот же месяц год назад). Это диагностическое сравнение продаж, не симуляция истинного упущенного спроса или уровня сервиса.

## API и приватность

- `GET /health`, `/api/suppliers`, `/api/options?supplier=iek`.
- `POST /api/plans` — `supplier`, необязательный `lead_time`, `safety`, `budget`, `category`, `warehouse`. Полный результат и `plan_id`.
- `POST /api/whatif` — те же параметры, три сценария.
- `POST /api/orders` — `plan_id`, выбранные `lines: [{code, quantity, unit_cost}]`, `note`.
- `GET /api/orders`, `/api/orders/{id}`; `POST /api/orders/{id}/approve` — `reviewer`, `verified_inputs: true`.
- `GET /api/orders/{id}/export` — только утверждённый заказ.
- `POST /api/alerts/scan` — параметры расчёта; `/api/alerts/settings` — настройки; `GET /api/alerts` — лента.

Для доступа вне доверенного локального компьютера настройте `API_KEY`, HTTPS на обратном прокси и ограничение сети. API-ключ передаётся заголовком `X-API-Key`; интерфейс хранит его только в текущем поле страницы. Локальная конфигурация не является системой персональных ролей: имя ответственного — запись подтверждения, не доказательство удостоверенной личности. Перед многопользовательской эксплуатацией подключите корпоративную аутентификацию.

LLM отключён по умолчанию. Для явного включения: `LLM_ENABLED=true`, `LLM_API_KEY`, при необходимости `LLM_BASE_URL` и `LLM_MODEL`. Наружу уходят только числа позиций/рисков для краткого текста, без наименований товаров, документов и клиентов. При ошибке остаётся детерминированное резюме. Числа заказа LLM не рассчитывает.

Структура: `backend/app/core` — загрузчики, расчёт, алерты; `datasets.py` — объединение и версия источников; `orders.py` — SQLite/CSV; `main.py` — API; `frontend` — интерфейс; `backend/tests` — проверки. `PRD.txt` — исходный план продукта, а не утверждение о фактически реализованных функциях.
